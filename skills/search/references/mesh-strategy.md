# MeSH strategy workflow

Three CLI subcommands + one strategy JSON artifact. The workflow is
**stateless, offline where possible, PRISMA-friendly**.

## Subcommands

### `sf-search mesh lookup`

Discover MeSH terms for each user-supplied concept.

```bash
sf-search mesh lookup --concept "diabetes" --concept "heart failure"
```

For each concept, calls:
- `esearch.fcgi?db=mesh&term=<concept>` → MeSH UIDs (top 5 candidates)
- `efetch.fcgi?db=mesh&id=<uid>&retmode=xml` → full tree

Emits NDJSON, one line per candidate:

```jsonc
{
  "concept_input": "diabetes",
  "rank": 1,
  "mesh_ui": "D003920",
  "mesh_term": "Diabetes Mellitus",
  "scope_note": "A heterogeneous group of disorders characterized by...",
  "tree_numbers": ["C18.452.394.750", "C19.246.267"],
  "parents": ["Glucose Metabolism Disorders", "Endocrine System Diseases"],
  "children": ["Diabetes Mellitus, Type 1", "Diabetes Mellitus, Type 2", "..."],
  "entry_terms": ["Diabetes", "Diabetic"]   // synonyms per MeSH
}
```

**Agent workflow**: the agent reads these candidates, picks the right
one per concept (`Diabetes Mellitus, Type 2` if user meant T2DM), and
proceeds to `mesh build`.

### `sf-search mesh build`

Pure local — **no network**. Assembles a strategy file from user's
picked MeSH terms and synonyms.

```bash
sf-search mesh build \
  --mesh "Diabetes Mellitus" --synonym diabetes --synonym diabetic \
  --mesh "Heart Failure" --synonym "cardiac failure" \
  --op AND \
  -o strategy.json
```

Repeat `--mesh` starts a new concept group. Each `--synonym` attaches
to the **most recent** `--mesh`. `--op` is the top-level operator
between concepts (default AND). Within a concept, MeSH term and
synonyms are OR'd.

### `sf-search mesh check`

Sanity-check the compiled strategy.

```bash
sf-search mesh check strategy.json
```

Calls:
- `espell.fcgi?db=pubmed&term=<pubmed_compiled>` → spelling suggestions
- `esearch.fcgi?db=pubmed&term=<pubmed_compiled>&rettype=count` → total count

Emits one JSON:

```jsonc
{
  "pubmed_count": 3421,
  "suggested_corrections": [],
  "compiled": {
    "pubmed":    "(\"Diabetes Mellitus\"[MeSH] OR diabetes[tiab] ...) AND (...)",
    "crossref":  "diabetes OR diabetic AND \"heart failure\" OR ...",
    "arxiv":     "all:diabetes OR all:diabetic AND all:\"heart failure\" ...",
    "openalex":  "diabetes OR diabetic AND \"heart failure\" OR ...",
    "s2":        "diabetes OR diabetic AND \"heart failure\" OR ..."
  }
}
```

### Executing the strategy

```bash
sf-search --from-strategy strategy.json --top 50
```

Reads `compiled.<source>` and runs each source with its own query.

## `strategy.json` schema

```jsonc
{
  "version": 1,
  "concepts": [
    {
      "mesh": "Diabetes Mellitus",
      "synonyms": ["diabetes", "diabetic"]
    },
    {
      "mesh": "Heart Failure",
      "synonyms": ["cardiac failure"]
    }
  ],
  "op": "AND",                  // AND | OR
  "compiled": {                 // auto-generated by `build`
    "pubmed":    "...",
    "crossref":  "...",
    "arxiv":     "...",
    "openalex":  "...",
    "s2":        "..."
  },
  "created_at": "2026-07-25T10:12:00Z",
  "tool": "sf-search",
  "tool_version": "0.1.0"
}
```

## Per-source compilation rules

Let `C_i = ("<mesh_i>"[MeSH] OR "<mesh_i>"[tiab] OR <syn1>[tiab] OR <syn2>[tiab] ...)`.

Overall strategy: `C_1 <op> C_2 <op> ... <op> C_n`.

**PubMed** (native syntax, precise):
```
("Diabetes Mellitus"[MeSH] OR "Diabetes Mellitus"[tiab] OR diabetes[tiab] OR diabetic[tiab])
AND
("Heart Failure"[MeSH] OR "Heart Failure"[tiab] OR "cardiac failure"[tiab])
```

**Crossref / OpenAlex / S2** (free-text approximation — no field
qualifiers, just terms and operators):
```
(diabetes OR diabetic OR "Diabetes Mellitus") AND ("Heart Failure" OR "cardiac failure")
```

**arXiv** (Atom syntax with `all:` field):
```
(all:diabetes OR all:diabetic OR all:"Diabetes Mellitus") AND (all:"Heart Failure" OR all:"cardiac failure")
```

The MeSH term itself is included in the free-text sources as a phrase
(dropping the `[MeSH]` qualifier that only PubMed understands).

## Rationale: why 3 subcommands and not 1

- **Statelessness**: each subcommand is a pure function of its inputs.
  Rerunnable, cacheable, agent-friendly.
- **Durable artifact**: `strategy.json` can be committed to a repo,
  reviewed by co-authors, cited in a systematic review's methods
  section. Meets PRISMA 2020 item 7 (search strategy reproducibility).
- **Agent-drivable**: `mesh lookup` → LLM decides → `mesh build` →
  optional `mesh check` → `--from-strategy`. Each step is a bounded,
  observable CLI call. No hidden state.
- **No LLM in skill**: concept splitting is a judgement call; the skill
  refuses to guess. The host agent (Claude / Codex / …) reads the
  request and decides.

## Non-medical topics

MeSH only indexes biomedical literature. For CS / physics / chemistry
topics, `mesh lookup` will return no candidates (or irrelevant ones);
the user should skip the `mesh` workflow entirely and use plain
positional or `--fields` mode. `mesh check` on a strategy for a
non-medical concept will typically show `pubmed_count: 0` — that's a
signal, not an error.
